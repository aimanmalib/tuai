# 0002: Claim pool, vault and receipt list

Status: accepted, 2026-11-17

## Context

A claim must pay `cumulative - alreadyClaimed` reward tokens to the locking bytecode in a Merkle leaf, exactly once
per increase, without the operator paying anything per claimant. Claim state has to live on chain, and a claimant
must not be able to reset it (for example by burning a receipt held in their own wallet).

## Decision

1. **Two contracts.**
   - `ClaimPool(poolCategory, rewardCategory, vaultBytecode, maxDepth)` holds one UTXO: the **state NFT** of the
     pool token category with the **minting** capability. Its `claim` function checks the whole transaction.
   - `PoolVault(poolCategory)` holds the reward tokens and the receipts. Its only function requires input 0 to carry
     the pool category's minting NFT. That NFT never leaves `ClaimPool` (every path recreates it at the same
     locking bytecode), so the `ClaimPool` script at input 0 decides every vault spend.
   - Splitting them keeps the large script out of every input: a claim spends three contract UTXOs, but only the
     state NFT input carries the 540-byte `ClaimPool` redeem script; the two vault inputs carry 39 bytes each.
2. **Capabilities tell UTXO types apart within the pool category.** State NFT = minting. Receipts = immutable
   (no capability; they are replaced, not edited, which the minting NFT in the same transaction permits).
   The pending-root NFT of the root gate (ADR 0003) will be the only mutable one.
3. **State commitment:** `root(32) || epoch(4, LE) || inputsHash(32)`, 68 bytes. Deploy writes a zero root with
   epoch 0: a zero root has no known preimage, so nothing is claimable until a real root is activated.
4. **Receipt commitment:** `key(32) || next(32) || claimed(8, LE)`, 72 bytes, with
   `key = sha256(lockingBytecode)`. Receipts form a singly linked list sorted by key read as a little-endian
   unsigned integer. Deploy creates the head `key = 0x00..00, next = 0xff..ff, claimed = 0`.
   - **First claim:** spends the predecessor `P` with `P.key < key < P.next`, which proves `key` has no receipt.
     Outputs `P` with `next = key` and a new receipt `(key, P.next, cumulative)`.
   - **Additional claim:** spends the receipt with `key` itself and outputs it with `claimed = cumulative`.
   - Because the list is strictly increasing and only `ClaimPool` can change it, a key can be inserted only once.
   Both commitments are above 40 bytes and rely on the 128-byte commitment limit of the 2026 VM, as do the
   proof loop and 33-byte key comparisons. The mock network and chipnet run that VM.
5. **Claim transaction layout** (fixed indexes keep the script short):

   | Index | Input | Output |
   |---|---|---|
   | 0 | state NFT (`ClaimPool.claim`) | state NFT, unchanged commitment, value and bytecode |
   | 1 | vault reward tokens | vault reward tokens minus the payment, same value |
   | 2 | vault receipt (own or predecessor) | updated receipt (predecessor or own), same value |
   | 3 | claimant funding | payment: reward tokens to the leaf's locking bytecode |
   | 4.. | more claimant funding | first claim: the new receipt; then claimant change |

   Inputs from index 3 on may not be the pool or the vault. Outputs after the receipts may not carry tokens.
6. **Who pays.** The claimant funds the payment output's dust, the new receipt's dust and the fee. Kept UTXOs
   (state, vault tokens, existing receipts) keep their exact satoshi value, so a claim cannot drain pool BCH.
   There is no minimum claim size.
7. **Amounts** are 8-byte little-endian in leaves and receipts and read with `OP_BIN2NUM`; the library limits
   them to `2^63 - 1` so they are always positive script numbers.
8. **One leaf per locking bytecode.** Receipts are keyed by locking bytecode, so the epoch builder must merge any
   duplicate before building a tree (the cumulative library already keys balances by locking bytecode).

## Measured

`reports/claim-sizes.json` is generated by `scripts/claim-sizes.ts` and checked by a test. At depth 9 (up to 512
leaves) the first claim is about 1.9 kB and an additional claim about 1.7 kB; each extra level adds 32 bytes.

## Consequences and known limits

- All claims spend the one state NFT, so claims are serialized; they can still chain inside one block. Sharding the
  reward tokens and the state over K UTXOs is a later option.
- The pool keeps at least one reward token unit: a vault output cannot hold zero fungible tokens. The deployer
  funds one unit more than the epoch budgets.
- Smaller transactions are possible (20-byte receipt keys, hand-tuned script); they are recorded as options, not
  taken, because the current layout is simpler to audit.
- Rejected alternatives: receipts in the claimant's wallet (burning it would allow a second claim); a bitmap of
  claimed indexes (indexes change between epochs while cumulative amounts do not); one contract for state and
  tokens (every input would carry the full script).
